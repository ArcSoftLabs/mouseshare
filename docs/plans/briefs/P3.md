# Task P3 — mutual authentication: verify `pair_ok`

Repository: current working directory. Test-first.

## Problem
Only the connector proves knowledge of the code/token. The target's `pair_ok` is accepted unverified (`app.py:_on_pair_ok`), so whoever answers at the address can become our client, receive our keystrokes, and (after later tasks) our clipboard and files. The `pairing.py` docstring claims both sides prove; make that true.

## Requirements
1. `pair_ok` gains `hmac`: HMAC-SHA256 keyed by the same secret the connector used (the pairing code for a fresh pairing, the stored token for `auth`), over the string `f"{nonce}|{target_id}|{initiator_id}|ok"` — note the reversed id order and the `|ok` suffix, so a captured `pair_proof` can never be replayed as a `pair_ok`. Put the function in `pairing.py` next to the existing proof, with the same constant-time compare.
2. The connector verifies it in `_on_pair_ok` **before** storing the token, publishing peers, or `_become_host`. A missing or wrong `hmac` → `_teardown("pair_ok not authenticated")` and a user-visible error, and the stored token (if any) is left untouched.
3. For a fresh pairing the connector keys the check with the code the user typed; for token `auth` with the stored token. The token minted by the target and delivered inside `pair_ok` is therefore only trusted after the HMAC passes.
4. **Compatibility:** a v2 peer (negotiated version 2, from P1) cannot send `hmac`. Accept `pair_ok` without `hmac` **only** when the negotiated version is 2, log a warning "peer <name> does not authenticate pair_ok (protocol v2)", and set a state flag `session.unauthenticated_peer = True` that the UI shows as a small warning. v3 peers must send it.
5. Do not log the code, token, nonce or hmac values.

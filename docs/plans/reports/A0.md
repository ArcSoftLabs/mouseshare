# A0 — Mac tap probe results (run by Benjamin, 2026-09-04)

`tools/mac_tap_probe.py` run twice in Terminal on the Mac mini (Accessibility and Input
Monitoring granted). Both runs agreed; the second run's `RESULT` lines are below, verbatim.

## Live symptom that prompted the run

Mac as host, Windows as client (app build at eec8c2a): the cursor never crosses over. The
Mac cursor keeps moving on the Mac screen while the Windows cursor is thrown against the
screen edges and stays pinned there; moving fast in all directions occasionally frees it
for a moment. This is exactly the failure predicted by the comment in
`InputCapture._start_mouse.handle_move` ("if it does not [stay parked], the offsets
accumulate and the peer cursor runs away"): every event reports `location - anchor`, the
sprite is not parked, so the reported deltas grow with the distance travelled. The brief
"coming loose" is `_moved`'s `limit` check firing and warping the cursor back to the anchor.

## Reading

1. **H1 confirmed.** A `kCGSessionEventTap` that deletes mouse-moved events does not stop
   the cursor sprite: after ~5 s of rightward motion the real cursor sat at x=2150, 870 px
   from the anchor, and `CGEventGetLocation` on the deleted events tracked it. Anchor-
   relative deltas are therefore wrong on macOS.
2. **`kCGMouseEventDeltaX/Y` are usable.** Their sum (868, 3) matches the location travel
   (865 px). They are integers; 64 % of events carry (0, 0) because the location moves in
   sub-pixel steps (0.23 px). Zero-delta events must simply not be reported.
3. **Decoupling pins the sprite but not the location field.** With
   `CGAssociateMouseAndMouseCursorPosition(False)` the real cursor stayed at the anchor
   (`cursor_after=(1280, 720)`, `NSEvent.mouseLocation` never moved) while delta fields
   kept arriving. `CGEventGetLocation` on the tapped events, however, kept integrating
   (first event already at (591, 689), 1092 px of travel) — so while decoupled the event
   location must not be used for anything.
4. **H2 refuted.** 4444 `CGEventPost` warps from inside the callback at ~900 events/s
   produced zero `kCGEventTapDisabledByTimeout`. Posting from the callback is safe on this
   macOS; it just does not park the cursor (`cursor_after=(441, 1025)`), so it is not a
   fix either. Posted events carry our PID (`own_warps_with_pid=4444`), so the existing
   injected-event passthrough keeps working.
5. Single display, `backing_scale=1.0`; CG and AppKit frames coincide here, so the A4
   multi-display conversion cannot be verified live on this Mac.

**Decision:** A2/A3 take the "H1 confirmed" branch of the plan (§4 Block A): decouple
during remote mode, take deltas from the event's delta fields inside the mouse intercept,
ignore the event location while suppressing, re-associate on every exit path. Brief:
`docs/plans/briefs/A3.md`.
